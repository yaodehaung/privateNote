# Linux Kernel `DEBUG_VM_PGTABLE`、Dynamic Debug 與 `pte_val()` 追蹤

**Author:** Nick Huang
**Date:** 2026-09-13

---

# 1. `pr_debug()` 是什麼？

Linux Kernel 可以使用：

```c
pr_debug("debug message\n");
```

輸出除錯訊息。

但 `pr_debug()` 和 `pr_info()` 不同，通常預設不會輸出。

例如：

```c
pr_info("info message\n");
pr_debug("debug message\n");
```

一般情況：

```text
pr_info()
   ↓
直接輸出

pr_debug()
   ↓
預設關閉
```

要控制 `pr_debug()`，可以使用 Linux Kernel 的 **Dynamic Debug** 機制。

---

# 2. 確認 Dynamic Debug

先檢查目前 Kernel：

```bash
grep CONFIG_DYNAMIC_DEBUG /boot/config-$(uname -r)
```

或在 Kernel source：

```bash
grep CONFIG_DYNAMIC_DEBUG .config
```

需要：

```text
CONFIG_DYNAMIC_DEBUG=y
```

如果沒有：

```bash
./scripts/config --enable DYNAMIC_DEBUG
make olddefconfig
```

之後重新 Build Kernel。

---

# 3. Dynamic Debug Control

Dynamic Debug 的控制介面通常可以從：

```text
/proc/dynamic_debug/control
```

或：

```text
/sys/kernel/debug/dynamic_debug/control
```

找到。

例如：

```bash
ls /proc/dynamic_debug/control
```

查看所有 Dynamic Debug callsite：

```bash
cat /proc/dynamic_debug/control
```

---

# 4. 開啟 `debug_vm_pgtable.c` 的 `pr_debug()`

例如：

```text
mm/debug_vm_pgtable.c
```

執行：

```bash
echo 'file mm/debug_vm_pgtable.c +p' | \
sudo tee /proc/dynamic_debug/control
```

其中：

```text
+p
```

代表啟用該 callsite 的輸出。

接著查看 Kernel log：

```bash
sudo dmesg -w
```

---

# 5. 確認 Dynamic Debug 是否成功 Enable

```bash
grep 'mm/debug_vm_pgtable.c' /proc/dynamic_debug/control
```

可能看到：

```text
mm/debug_vm_pgtable.c:xxx [kernel]function_name =p "message"
```

其中：

```text
=_    → disabled
=p    → enabled
```

---

# 6. 關閉 `pr_debug()`

```bash
echo 'file mm/debug_vm_pgtable.c -p' | \
sudo tee /proc/dynamic_debug/control
```

---

# 7. Reboot 後保留 Dynamic Debug

Runtime 執行：

```bash
echo 'file mm/debug_vm_pgtable.c +p' > /proc/dynamic_debug/control
```

只修改目前 Kernel 的 runtime 狀態：

```text
+p
 ↓
目前有效
 ↓
reboot
 ↓
設定消失
```

如果希望重新開機之後仍然自動 Enable，需要使用 Kernel Command Line。

# 8. 使用 `dyndbg` Kernel Parameter

編輯 GRUB：

```bash
sudo nano /etc/default/grub
```

找到：

```text
GRUB_CMDLINE_LINUX_DEFAULT="..."
```

加入：

```text
dyndbg="file mm/debug_vm_pgtable.c +p"
```

例如：

```text
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash dyndbg=\"file mm/debug_vm_pgtable.c +p\""
```

更新：

```bash
sudo update-grub
sudo reboot
```

查看 Kernel command line：

```bash
cat /proc/cmdline
```

# 10. 為什麼 `debug_vm_pgtable` 建議 Boot 時 Enable？

如果 `debug_vm_pgtable` 在 Kernel initialization 階段執行：

```text
Kernel Boot
     ↓
Dynamic Debug
     ↓
debug_vm_pgtable()
     ↓
Page Table Helper Tests
     ↓
pr_debug()
     ↓
Boot 完成
```

如果 Linux Boot 完才執行：

```bash
echo 'file mm/debug_vm_pgtable.c +p' > /proc/dynamic_debug/control
```

可能已經太晚：

```text
Kernel Boot
     ↓
debug_vm_pgtable()
     ↓
pr_debug() disabled
     ↓
測試完成
     ↓
Linux Boot 完成
     ↓
使用者設定 +p
```

因此 `debug_vm_pgtable` 這類 boot/init 階段的程式，使用：

```text
dyndbg="file mm/debug_vm_pgtable.c +p"
```

會比較適合。

# 12. `DEBUG_VM_PGTABLE` 是做什麼？

`CONFIG_DEBUG_VM_PGTABLE` 的主要用途是：

> 測試各 Architecture 實作的 Page Table Helper 是否符合 Linux MM Core 預期的語意。

例如會涉及：

```c
pte_young()
pte_mkyoung()
pte_mkold()

pte_dirty()
pte_mkdirty()
pte_mkclean()

pte_write()
pte_mkwrite()
pte_wrprotect()
```

概念：

```text
建立測試 PTE
      ↓
pte_mkyoung()
      ↓
pte_young()
      ↓
應該為 true
      ↓
pte_mkold()
      ↓
pte_young()
      ↓
應該為 false
```

因此它不是用來直接查看某個 Process 的 Page Table。

---

# 13. `DEBUG_VM_PGTABLE` vs `PTDUMP_DEBUGFS`

兩者用途不同：

| Config                    | 用途                     |
| ------------------------- | ---------------------- |
| `CONFIG_DEBUG_VM_PGTABLE` | 測試 Page Table Helper   |
| `CONFIG_PTDUMP_DEBUGFS`   | Dump Kernel Page Table |

## `DEBUG_VM_PGTABLE`

```text
CONFIG_DEBUG_VM_PGTABLE
        ↓
Page Table Helper Self-test
        ↓
PTE / PMD / PUD
        ↓
pte_young()
pte_mkyoung()
pte_mkold()
pte_dirty()
...
```

## `PTDUMP_DEBUGFS`

```text
CONFIG_PTDUMP_DEBUGFS
        ↓
Page Table Dump
        ↓
debugfs
        ↓
kernel_page_tables
```

如果 Architecture 支援：

```bash
./scripts/config --enable PTDUMP_DEBUGFS
make olddefconfig
```

確認：

```bash
grep CONFIG_PTDUMP .config
```

可能看到：

```text
CONFIG_PTDUMP_CORE=y
CONFIG_PTDUMP_DEBUGFS=y
```

重新 Boot 後，可以查看：

```bash
sudo cat /sys/kernel/debug/kernel_page_tables
```

# 14. `pte_t` 是什麼？

Linux Kernel 使用：

```c
pte_t
```

表示 Page Table Entry。

`pte_t` 通常不是直接使用：

```c
unsigned long
```

而是由各 Architecture 定義的型別。

Linux Page Table hierarchy 常見為：

```text
PGD
 ↓
P4D
 ↓
PUD
 ↓
PMD
 ↓
PTE
 ↓
Physical Page
```

對應型別：

```c
pgd_t
p4d_t
pud_t
pmd_t
pte_t
```

---

# 15. `pte_val()` 是什麼？

`pte_val()` 用來：

> 從 `pte_t` 取得底層 Raw PTE Value。

例如：

```c
pte_t pte;
pteval_t value;

value = pte_val(pte);
```

概念：

```text
        pte_val()
pte_t ─────────────→ Raw PTE Value
```

例如：

```text
pte_t
 │
 └── raw bits
      0x8000000012345067
```

執行：

```c
pte_val(pte)
```

得到：

```text
0x8000000012345067
```

---

# 16. Raw PTE Value 裡有什麼？

PTE 不只是 Physical Address。

通常還包含：

```text
PTE Raw Value
│
├── PFN / Physical Address
│
├── Present
├── Read / Write
├── User / Supervisor
├── Accessed / Young
├── Dirty
├── Execute Permission
└── Architecture-specific Bits
```

實際 bit layout 是 Architecture-specific。

例如：

```text
x86
arm64
riscv
m68k
```

都可能不同。

---

# 17. 為什麼 Linux 要使用 `pte_t`？

Linux 不希望 MM Core 直接假設：

```c
unsigned long pte;
```

而是統一使用：

```c
pte_t
pmd_t
pud_t
p4d_t
pgd_t
```

搭配：

```c
pte_val()
pmd_val()
pud_val()
p4d_val()
pgd_val()
```

概念：

```text
Page Table Entry Type
        │
        ├── pte_t → pte_val()
        ├── pmd_t → pmd_val()
        ├── pud_t → pud_val()
        ├── p4d_t → p4d_val()
        └── pgd_t → pgd_val()
```

這樣 Common MM Code 不需要知道不同 Architecture 的底層資料結構。

---

# 18. `pte_val()` 與 `__pte()`

兩者方向相反。

```text
              pte_val()
       ┌────────────────────→
       │
     pte_t                Raw Value
       │
       ←────────────────────┘
               __pte()
```

例如：

```c
pte_t pte;
pteval_t value;

value = pte_val(pte);

pte = __pte(value);
```

可以簡單記成：

```text
pte_val()
    =
pte_t → raw value
```

以及：

```text
__pte()
    =
raw value → pte_t
```

---

# 19. `pte_val()` 與 `pte_young()`

`pte_young()` 用來判斷 PTE 是否具有 Young / Accessed 狀態。

Architecture 的實作概念上可能類似：

```c
static inline int pte_young(pte_t pte)
{
    return pte_val(pte) & ACCESS_BIT;
}
```

流程：

```text
pte_t
 │
 ▼
pte_val()
 │
 ▼
Raw PTE Bits
 │
 ▼
檢查 Accessed / Young Bit
 │
 ▼
pte_young()
```

---

# 20. `pte_val()` 與 `pte_mkold()`

`pte_mkold()`：

```text
mkold = make old
```

主要用途是清除 PTE 的 Young / Accessed 狀態。

概念：

```text
pte_t
 │
 ▼
取得 Raw PTE Bits
 │
 ▼
Clear Young / Accessed Bit
 │
 ▼
重新形成 pte_t
 │
 ▼
pte_mkold()
```

因此：

```text
              pte_t
                │
                ▼
            pte_val()
                │
                ▼
           Raw PTE Bits
                │
        ┌───────┴────────┐
        ▼                ▼
   pte_young()       pte_mkold()
        │                │
   Check Young       Clear Young
```

---

# 21. `pte_val()` 是 Architecture-specific

`pte_val()` 並不是所有 Architecture 共用完全相同的實作。

通常要追：

```text
arch/<ARCH>/include/asm/
```

例如：

```text
arch/x86/include/asm/
arch/arm64/include/asm/
arch/riscv/include/asm/
arch/m68k/include/asm/
```

因此看到：

```c
pte_val(pte)
```

時，要往對應 Architecture 的 Header 找。

# 23. m68k 為什麼在 `pgtable.h` 找不到？

例如查看：

```text
arch/m68k/include/asm/pgtable.h
```

可能沒有直接看到：

```c
#define pte_val(x) ...
```

這不代表 m68k 沒有 `pte_val()`。

原因是：

> `pte_val()` 不一定直接定義在 `arch/m68k/include/asm/pgtable.h`。

它可能透過其他 Header 間接提供。

例如：

```text
arch/m68k/include/asm/pgtable.h
              │
              │ #include
              ▼
      Other m68k Header
              │
              ▼
          pte_t
          pte_val()
```

這就是 C Header 的：

> Transitive Include（間接 Include）

# 26. `<asm/pgtable.h>` 如何知道要用 m68k？

Source Code 可能只有：

```c
#include <asm/pgtable.h>
```

但實際使用哪個 Architecture，不是 Preprocessor 自己判斷。

而是 Kbuild 根據：

```bash
make ARCH=m68k
```

設定 Architecture-specific include path。

概念：

```text
make ARCH=m68k
       │
       ▼
Kbuild
       │
       ▼
Architecture Include Path
       │
       ▼
arch/m68k/include
       │
       ▼
#include <asm/pgtable.h>
       │
       ▼
arch/m68k/include/asm/pgtable.h
```

所以：

```c
#include <asm/pgtable.h>
```

在：

```text
ARCH=x86
```

會對應：

```text
arch/x86/include/asm/pgtable.h
```

在：

```text
ARCH=m68k
```

則對應：

```text
arch/m68k/include/asm/pgtable.h
```

---

# 27. m68k 的 Include Chain

某個 source 可能：

```c
#include <linux/mm.h>
```

然後間接形成：

```text
m68k source
     │
     ▼
<linux/mm.h>
     │
     ▼
Linux MM Headers
     │
     ▼
<asm/pgtable.h>
     │
     ▼
arch/m68k/include/asm/pgtable.h
     │
     ▼
其他 m68k Header
     │
     ▼
pte_t / pte_val()
```

所以：

> 不要只在單一 `pgtable.h` 裡搜尋。

# 28. `DEBUG_VM_PGTABLE` 與 `pte_val()` 的關係

`DEBUG_VM_PGTABLE` 會測試 Architecture 提供的 Page Table Helper。

例如：

```text
DEBUG_VM_PGTABLE
       │
       ▼
建立測試 PTE
       │
       ▼
pte_mkyoung()
       │
       ▼
pte_young()
       │
       ▼
pte_mkold()
       │
       ▼
pte_young()
```

而這些 Architecture Helper 底層會操作：

```text
pte_t
 ↓
Raw PTE Bits
```

因此研究：

```text
DEBUG_VM_PGTABLE
```

最後很自然會一路追到：

```text
pte_t
 ↓
pte_val()
 ↓
pte_young()
 ↓
pte_mkold()
 ↓
Architecture Page Table Implementation
```

# 32. 重點整理

可以把整個研究方向記成：

```text
CONFIG_DEBUG_VM_PGTABLE
        ↓
測試 Page Table Helper
        ↓
pte_t
        ↓
pte_val()
        ↓
Raw PTE Bits
        ↓
pte_young()
pte_mkold()
pte_dirty()
...
        ↓
Architecture-specific implementation
        ↓
arch/<ARCH>/include/asm/
```

而要觀察 `debug_vm_pgtable` 本身的執行：

```text
pr_debug()
    ↓
Dynamic Debug
    ↓
dyndbg=
    ↓
Kernel Boot
    ↓
debug_vm_pgtable()
    ↓
dmesg
```

最重要的兩個觀念是：

1. `DEBUG_VM_PGTABLE` 是用來測試 Architecture Page Table Helper，不是單純 dump Page Table。
2. `pte_val()`、`pte_young()`、`pte_mkold()` 等底層實作通常是 Architecture-specific，因此研究 m68k 時要從 `arch/m68k/include/asm/` 以及其 include chain 往下追。
