# 一文徹底搞懂 kmalloc 的底層機制：從 SLUB Cache 到 Buddy Allocator 的全鏈路解析

最近在翻 Linux Kernel 記憶體管理的實作，把 `kmalloc()` 一路追到 SLUB allocator，整個流程其實比想像中更「工程化」。

這篇文章把我的理解整理出來，如果你平常寫 driver 或 kernel module，應該會很有感。

---

## 1. kmalloc 是什麼？一句話定位

`kmalloc` 是 Linux kernel 裡最常用的記憶體配置 API，核心特性是：

> **從 kernel 空間取得「實體連續」的小型記憶體，並透過 slab（SLUB）機制加速配置。**

你可以把它理解成：

👉 **「kernel 版的 malloc + cache pool 加速器」**

但它跟 user space 的 `malloc()` 最大差異是：

- malloc → libc → brk / mmap → kernel  
- kmalloc → **直接走 kernel allocator（SLUB）**

---

## 2. 整體架構概覽：kmalloc 只是入口

很多人一開始會誤會：

> kmalloc = 記憶體分配器

但其實它只是入口而已👇

```
kmalloc()
   ↓
SLUB allocator（slab layer）
   ↓
Buddy allocator（page allocator）
   ↓
Physical memory
```

整體可以分成三層：

| 層級 | 負責什麼 |
|------|--------|
| kmalloc API | 對外介面（size-based allocation） |
| SLUB | object cache 管理 |
| Buddy system | page 級別記憶體管理 |

---

## 3. SLUB 核心概念：記憶體不是「分配」，是「拿現成的」

SLUB 的設計哲學其實很簡單：

> **不要每次分配記憶體，而是預先切好一堆「物件」，需要時直接拿。**

👉 **object cache（物件快取）**

---

## 4. kmalloc 與 SLUB cache 的關係（關鍵重點）

### 4.1 系統預先建立 kmalloc caches

```
kmalloc-8
kmalloc-16
kmalloc-32
kmalloc-64
kmalloc-128
kmalloc-256
kmalloc-512
kmalloc-1024
...
```

---

### 4.2 kmalloc 的 size 對齊機制

```c
kmalloc(100, GFP_KERNEL);
```

```
100 → 對齊到 128
→ 使用 kmalloc-128 cache
```

---

### 4.3 cache 裡的記憶體怎麼來？

```
SLUB cache 不夠
   ↓
向 buddy allocator 要 page（通常 4KB）
   ↓
切成固定大小 object
   ↓
放入 freelist
```

---

### 4.4 kmalloc 真正的配置流程

```
kmalloc(size)
   ↓
找到對應 kmalloc cache
   ↓
從 freelist 拿一個 object
   ↓
回傳
```

---

### 4.5 kfree 並不會真的釋放記憶體

```c
kfree(ptr);
```

```
ptr → 回到 cache freelist
```

## 7. 為什麼不直接用 Buddy Allocator？

- 單位太大（page）
- fragmentation
- 成本高

## 12. /proc/slabinfo：觀察 kmalloc / SLUB 的最佳入口

在實際系統中，你可以透過 `/proc/slabinfo` 直接觀察 SLUB 的運作狀況：

```bash
cat /proc/slabinfo
```

輸出範例（簡化）：

```
kmalloc-128    1024   2048    128   ...
kmalloc-256     512   1024    256   ...
```

欄位重點說明：

| 欄位 | 說明 |
|------|------|
| name | cache 名稱 |
| active_objs | 正在使用的 object 數量 |
| num_objs | 總 object 數量 |
| objsize | 每個 object 大小 |

---

### 如何解讀？

例如：

```
kmalloc-128  1024  2048  128
```

代表：

- 128 bytes 的 cache
- 總共有 2048 個 object
- 目前使用 1024 個
- 剩下 1024 個在 freelist

👉 這就對應到我們前面講的：

- freelist（可用）
- in-use objects（正在使用）

## 13. 補充總結

`/proc/slabinfo` 就是 SLUB 的即時監控介面：

👉 **讓你看到 kmalloc cache 的實際運作狀態**

搭配：

- `kmalloc()` 行為

你可以從「理論」直接對到「系統實際狀況」

## 12. 觀察 SLUB 狀態：/proc/slabinfo

在實際系統中，你可以透過以下指令觀察目前 SLUB 的配置狀況：

```bash
sudo cat /proc/slabinfo
```

這個檔案會列出所有 slab cache 的資訊，例如：

- cache 名稱（kmalloc-64、kmalloc-128...）
- active objects（正在使用的物件數）
- total objects（總物件數）
- object size
- slabs 數量

範例（簡化）：

```
kmalloc-128  1024  2048  128  ...
kmalloc-256   512  1024  256  ...
```

你可以用來觀察：

- 哪些 size 的 kmalloc 使用最頻繁
- slab 是否有過多未使用（fragmentation / 浪費）
- 系統記憶體分配行為

👉 這在 debug kernel memory issue 或效能分析時非常有用
